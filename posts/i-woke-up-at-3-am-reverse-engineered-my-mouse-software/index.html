I Woke Up at 3 AM and Decided to Reverse-Engineer My Mouse Software

Nobody asked me to do this. No deadline, no client, no assignment. It was 3 AM, my room was dark except for the monitor, and I had one stupid problem: my EvoFox mouse had no way to be configured on my Linux setup.

I’d just moved to Omarchy (Arch + Hyprland, if you haven’t seen it, go look), and everything felt perfect. Fast, clean, mine. Except my mouse was stuck on whatever settings it had last been given on Windows. DPI, polling rate, button mapping, lighting, all locked behind one .exe file sitting in my Downloads folder.

I stared at it for a while. Then I thought: what even is inside this thing?

That’s the whole origin story. No grand plan. Just curiosity and bad sleep habits.

The “Why Am I Doing This?” Moment

Around 3:30 AM I genuinely asked myself why I was awake. I could have booted into Windows for two minutes, changed the settings, and gone to bed. Problem solved.

But that’s the thing about people like us. The fix was never the point. The point was “how does this actually work?” The moment you see a black box, something in your brain refuses to let it stay black.

And honestly, there was a quieter reason too. I was tired of Linux being the platform that gets left behind. Hardware companies ship one Windows-only tool and call it a day. A mouse is not rocket science. If I could figure out how it talks, I could fix this for myself, and maybe for anyone else with the same mouse and the same 3 AM problem.

Step 1: Meet the Enemy

First thing I did was not run it. Old habit: you don’t just double-click mystery executables at 3 AM.

A PE32 executable for Windows, as expected. The strings output gave me the first real hints. Device names, UI labels, and the DLL names it pulled in. When I looked at the import table, a few of them stood out: calls to the Windows HID stack and device enumeration APIs.

That was the moment I relaxed a little. If a mouse tool is using HID APIs, it means the whole conversation between the software and the mouse is happening over USB HID reports. No secret driver, no kernel module, no black magic. Just bytes going back and forth over a wire. And Linux already knows how to speak HID perfectly well.

Step 2: Figuring Out What the App Actually Says to the Mouse

This is the part that makes the whole thing worth it.

A configuration tool for a gaming mouse does basically three things:

  1. Finds the device by its USB vendor ID and product ID.
  2. Sends feature or output reports to change a setting (DPI stage, report rate, button binding, LED mode).
  3. Reads reports back so the UI can show the current state.

So the job was to extract:

  • the VID/PID the app looks for,
  • the report IDs and the byte layout of each command,
  • and the order it sends them in during a normal “apply settings” action.

The Part Where It All Went Wrong (and Was Kind of Funny)

My first attempt at the rebuild was a disaster, and I have to tell you about it, because it’s the best part of the story.

I let my tooling take a first pass at “porting” the app. I came back, launched the result, and saw a window titled re-engineered-app. It had a menu that said File and Help. It had a big status box that said “Application started successfully.” And at the bottom, three buttons: Check System, About, Exit.

That’s it. That was my “ported EvoFox software.”

No DPI slider. No button mapping. No lighting. No mouse. Just a polite little window pretending it had done something, with an Exit button in case I wanted to leave.

I sat there at 6 AM, half laughing, half genuinely annoyed. Why do I need a Check System button? What system? What am I checking?

But it taught me something important. A rebuild is not a port until it does what the original does. A window that launches is not an application. A UI that looks nothing like the original, talking to nothing, is just a very confident piece of nothing.

So I scrapped the approach, wrote down exactly what “done” would mean, and started over with real rules:

  • Every screen of the original has to exist in the new one.
  • Every feature has to either work or be honestly marked as not working.
  • It has to detect the actual mouse and send the actual commands.
  • No placeholder screens. Ever.

Painful lesson, but a good one. If you don’t define “finished,” you’ll get “it compiles” and call it a win.

Step 3: Rebuilding It Properly

Once I understood the original’s structure, the rebuild became much more honest work:

  • UI: recreated screen by screen, using the original’s layout and assets as the reference, not my imagination.
  • Device layer: a small hidraw backend that opens the device, sends the report bytes, and parses what comes back.
  • Permissions: the udev rule above, shipped with the project, so it works on a fresh machine.
  • Packaging: a PKGBUILD and a .desktop entry, so on Omarchy it installs like a normal app and shows up in the launcher with an icon. Because if I’m doing this, I want it to feel native, not like a hack.

Seeing the DPI value change on my actual mouse, from my actual Linux desktop, from code I understood end to end? I’m not going to pretend that wasn’t a great feeling. Four in the morning energy, but the good kind.

What I Actually Learned

A few things stuck with me from this night:

Hardware is simpler than it looks. Most peripherals are just structured bytes over a standard protocol. The mystery is mostly in the packaging.

Static analysis first, always. Strings, imports, resources. You learn a surprising amount before running a single instruction.

Define “done” before you start. My fake Check System app is the proof.

You don’t need a reason. I didn’t do this for a job, a grade, or a portfolio line. I did it because I was curious and the problem was annoying. Some of the best things I’ve learned came from exactly that kind of night.

The Code

Everything is open. The reverse engineering notes, the protocol documentation, the app, the udev rules, and the Arch package are all in the repo:

github.com/ArenRedd/EvoFox-Port

If you own an EvoFox mouse and you’re on Linux, try it and tell me what breaks. Open an issue, send a pull request, or just tell me your mouse model. If you’re a student wondering where to start with reverse engineering, honestly, pick something small that annoys you personally. A mouse. A keyboard. A cheap gadget with a Windows-only app. Start with strings, follow the imports, and see where it leads.

It’s 3 AM somewhere right now, and someone is looking at an .exe they don’t understand. This is for them.

Keep breaking things. Keep asking why.
